# AtlasIS — План реализации целевой архитектуры v1

**Статус:** проект на согласование  
**Основа:** ветка `feat/authorization-model`, commit `2cf7bc8`  
**Область:** backend, PostgreSQL, API, авторизация, миграция данных, документация и frontend  
**Принцип:** сначала согласование модели и плана миграции, затем реализация небольшими проверяемыми изменениями.

## 1. Цель

Развить текущую реализацию AtlasIS в реестр информационных систем (ИС) и объектов информационной инфраструктуры (ОИИ) организаций холдинга с изоляцией арендаторов (tenants), разграничением доступа, управлением изменениями через Change Request (CR), неизменяемыми версиями и сохраняемой историей.

Реализация должна учитывать применимые требования законодательства Республики Беларусь и нормативных документов ОАЦ, включая постановку требований к атрибутам реестра на основе приказов № 66 и № 130. Конкретные нормативные требования необходимо проверить и связать с полями, проверками и доказательствами соответствия до утверждения окончательной схемы данных.

## 2. Архитектурные решения, принятые для v1

1. **ИС и ОИИ — разные доменные сущности.** У них независимые идентификаторы, атрибуты, владельцы, права и версии.
2. **Терминология утверждена:** ОИИ означает «объект информационной инфраструктуры»; КВОИ («критически важный объект информатизации») — отдельный формальный нормативный статус, а не синоним ОИИ. «Объект информатизации» не вводится как третья основная сущность AtlasIS в рамках текущего решения.
2. **Связь ОИИ → ИС:** одно ОИИ может содержать несколько ИС, одна ИС может входить в несколько ОИИ. Вложенные ОИИ в v1 не поддерживаются.
3. **Состав ОИИ не наследует права.** Включение ИС в ОИИ не меняет владельца ИС, её атрибуты или доступ к ней.
4. **Состав ОИИ изменяется через CR ОИИ.** Снимок состава входит в версию ОИИ. Не допускается независимый изменяемый список состава, выступающий вторым источником истины.
5. **Один CR изменяет одну сущность.** Для изменения состава используется CR целевого ОИИ; атомарные CR для нескольких сущностей в v1 не реализуются.
6. **Tenant — граница изоляции.** Запросы, поиск, счётчики, экспорт и справочные операции не должны раскрывать данные другого tenant.
7. **Организация принадлежит ровно одному tenant.** Организации не обязаны образовывать дерево; связи между ними типизированы.
8. **Права имеют явную область действия.** Tenant-wide доступ назначается отдельно; полномочия на управление составом ОИИ выделяются в отдельное действие `manage_composition`.
9. **Версии неизменяемы.** Применение CR создаёт следующую версию, сохраняет предыдущую и атомарно обновляет ссылку на текущую версию.
10. **Идентификаторы разделены по назначению.** Для новых сущностей используются технические UUIDv7 и отдельные отображаемые номера. Номера ИС и ОИИ имеют отдельные пространства нумерации в рамках tenant и типа сущности. Пропуски допустимы; повторное использование номеров запрещено.
11. **Legacy-идентификаторы IA сохраняются** как миграционные ссылки до утверждения и выполнения отдельной стратегии сопоставления.
12. **Идентификация пользователей — через Keycloak/OIDC.** Внутренний subject отделён от изменяемых атрибутов AD. Источник actor для операций определяется по проверенной идентичности, а не по недоверенному полю запроса.
13. **PostgreSQL RLS — дополнительный уровень защиты**, а не замена авторизации на уровне приложения.
14. **История и аудит сохраняются.** Политика удаления и хранения данных должна учитывать требования к аудиту и ретенции.

## 3. Текущее состояние и основные разрывы

| Область | Текущее состояние | Требуемое изменение |
|---|---|---|
| Домен активов | `InformationAsset` объединяет ИС и ОИИ | Разделить доменные модели |
| Идентификаторы | `IA00000`, единая последовательность | UUIDv7 и отдельная нумерация ИС/ОИИ |
| PostgreSQL | Общие таблицы `information_assets` и `information_asset_versions` | Раздельные типизированные сущности и связи |
| Tenants и организации | Нет полноценной модели в миграциях `0001–0005` | Добавить справочники и ограничения изоляции |
| Владение | Часть ссылок хранится текстовыми полями без FK | Ввести типизированные ссылки и ограничения целостности |
| Состав ОИИ | Отдельная модель отсутствует | Реализовать связь ОИИ–ИС и её историю через версии |
| CR | Одно поле `asset_id`, есть `base_version` | Перевести на явную целевую сущность и сохранить optimistic locking |
| Approval | Есть модель согласования и ограничения статусов | Увязать с новой моделью CR и авторизацией |
| Обсуждения | Есть доменные типы, но нет полноценного persistence в миграциях `0001–0005` | Добавить сохраняемые обсуждения и комментарии |
| Авторизация | Начальная RBAC-реализация | Tenant-aware authorization и явные области назначения |
| OIDC | Полноценная интеграция отсутствует | Интегрировать Keycloak/OIDC и проверенный principal |
| API | Существуют legacy endpoints `/assets` | Утвердить переход к типизированным API и совместимость |
| Frontend | Начальная заготовка Vue | Реализовать рабочие экраны реестра и согласования |
| Документация | Часть описаний и roadmap расходится с кодом | Синхронизировать документы с фактическим состоянием |

## 4. Этапы реализации

### Этап 0. Зафиксировать baseline и карту зависимостей

**Затрагиваемые области:**
- `backend/internal/domain/`
- `backend/internal/application/`
- `backend/internal/authorization/`
- `backend/internal/infrastructure/authorization/`
- `backend/internal/infrastructure/postgres/`
- `backend/internal/httpapi/`
- `backend/internal/ports/`
- `backend/migrations/0001_initial.sql` — `0005_approval_id_sequence.sql`
- `docs/api/openapi.yaml`
- `docs/architecture/`
- `docs/domain/`
- `docs/roadmap.md`

**Работы:**
- Зафиксировать базовый commit и перечень существующих миграций.
- Составить карту зависимостей домена, application services, API и PostgreSQL.
- Зафиксировать действующие инварианты и тесты, которые должны сохраниться.
- Сверить roadmap с кодом, не помечая функциональность выполненной только на основании наличия доменных типов.

**Результат:** актуальная инвентаризация и матрица текущего/целевого состояния.

**Критерий приёмки:** для каждой крупной области определены текущая реализация, разрывы, зависимости и тесты.

### Этап 1. Утвердить целевую модель данных

**Работы:**
- Описать сущности Tenant, Organization, InformationSystem, InformationInfrastructureObject, версии, CR, согласования, обсуждения, назначения ролей и аудит.
- Определить связи и правила удаления.
- Утвердить способ хранения состава ОИИ в версиях.
- Уточнить атрибуты ИС и ОИИ с привязкой к применимым требованиям приказов ОАЦ № 66 и № 130.
- Определить обязательность, типы, допустимые значения, источники данных и правила валидации атрибутов.
- Определить отображаемые номера и технические ключи.
- Разделить обязательные атрибуты реестра и вычисляемые показатели.

**Ограничения:**
- Не использовать `COUNT(*) + 1` для выдачи номеров.
- Не применять универсальные ссылки `object_type + object_id` там, где необходимы внешние ключи.
- Не вводить EAV-модель для обычных атрибутов.
- JSONB допустим для типизированных значений полей CR при строгой валидации, но не как замена реляционным связям.

**Результат:** согласованные ER-модель, словарь атрибутов и правила целостности.

**Критерий приёмки:** схема описывает все сущности, ключи, ограничения, владение, версии, состав ОИИ и область действия прав.

### Этап 2. Спроектировать миграцию существующих данных

**Работы:**
- Сопоставить существующие IA-записи с будущими ИС и ОИИ.
- Определить, как преобразуются текущие версии, CR, согласования и ссылки.
- Разработать правила обработки некорректных, неполных и неоднозначных данных.
- Определить, как назначаются tenant и организация для существующих записей.
- Установить порядок переноса обсуждений, если они появятся до миграции.
- Предусмотреть проверку количества записей, ссылочной целостности, истории и текущих версий.
- Разработать план отката и критерии остановки миграции.

**Результат:** отдельный документ с mapping-таблицами, правилами преобразования и планом перехода.

**Критерий приёмки:** для каждой legacy-сущности определён однозначный результат либо формализованный процесс ручного разрешения неоднозначности.

### Этап 3. Реализовать фундамент tenant и типизированных сущностей

**Основные области кода:**
- `backend/internal/domain/asset/`
- `backend/internal/application/asset/`
- `backend/internal/ports/`
- `backend/internal/infrastructure/postgres/`
- `backend/internal/httpapi/`
- новые миграции после `0005`

**Работы:**
- Ввести отдельные доменные сущности ИС и ОИИ.
- Реализовать Tenant и Organization с внешними ключами и ограничениями.
- Добавить отдельные пространства отображаемых номеров.
- Реализовать типизированные репозитории и операции чтения/записи.
- Добавить связь ОИИ–ИС с ограничениями на tenant, тип сущности и отсутствие вложенных ОИИ.
- Обеспечить tenant-фильтрацию в каждом запросе к данным.

**Критерий приёмки:** нельзя создать некорректную связь между сущностями, получить запись другого tenant или обойти целостность через прямую запись в БД.

### Этап 4. Адаптировать версионирование и CR

**Основные области кода:**
- `backend/internal/domain/change/`
- `backend/internal/application/change/`
- `backend/internal/domain/approval/`
- `backend/internal/application/approval/`
- `backend/internal/infrastructure/postgres/`
- `backend/internal/httpapi/`

**Работы:**
- Перейти к явному указанию целевого типа и идентификатора сущности в CR.
- Сохранить правило «один CR — одна сущность».
- Для CR ОИИ включить состав ИС в снимок версии ОИИ.
- Сохранить optimistic locking, проверку `base_version`, блокировки строк и атомарность применения.
- Исключить изменение опубликованных версий.
- Пересмотреть ограничения `ON DELETE CASCADE` для истории, аудита и согласований.

**Критерий приёмки:** параллельные изменения не приводят к потере обновлений; неудачное применение CR не оставляет частично записанную версию или состав.

### Этап 5. Реализовать обсуждения и аудит

**Основные области кода:**
- `backend/internal/domain/discussion/`
- `backend/internal/application/`
- `backend/internal/infrastructure/postgres/`
- новые миграции
- тесты persistence и API

**Работы:**
- Реализовать хранение обсуждений, комментариев и их связи с родительским объектом.
- Обеспечить сохранение авторства и времени.
- Определить правила редактирования, удаления и хранения истории.
- Фиксировать изменения состава ОИИ и связь с CR.
- Зафиксировать существенные события жизненного цикла CR и согласования.

**Критерий приёмки:** обсуждения и события переживают перезапуск сервиса, имеют проверяемое авторство и не исчезают при обычном удалении связанных бизнес-данных.

### Этап 6. Реализовать авторизацию и интеграцию OIDC

**Основные области кода:**
- `backend/internal/authorization/`
- `backend/internal/infrastructure/authorization/`
- `backend/internal/httpapi/`
- `backend/internal/ports/`
- конфигурация сервиса и тесты безопасности

**Работы:**
- Интегрировать проверку токенов Keycloak/OIDC.
- Получать actor только из проверенного principal.
- Хранить внутренний UUID subject и внешний ключ `(iss, sub)`.
- Не использовать `sAMAccountName`, email или display name как единственный ключ пользователя.
- Реализовать назначения ролей с явной областью действия.
- Реализовать tenant-wide права отдельным назначением.
- Разделить права на просмотр, редактирование через CR, согласование, применение CR и управление составом ОИИ.
- Применять одинаковые правила авторизации к API, поиску, экспорту, счётчикам и справочным операциям.
- При необходимости добавить PostgreSQL RLS как дополнительную защиту.

**Критерий приёмки:** отрицательные тесты подтверждают запрет межтенантного доступа и действий без необходимых полномочий. Подмена actor в запросе не позволяет совершить операцию от имени другого пользователя.

### Этап 7. Утвердить и реализовать API-переход

**Основной документ:** `docs/api/openapi.yaml`

**Работы:**
- Определить целевые endpoints для ИС, ОИИ, состава, версий, CR, согласований и обсуждений.
- Утвердить стратегию для legacy `/assets` и `/assets/{assetId}`.
- Определить сроки и условия совместимости старых клиентов.
- Исключить передачу доверенного actor через произвольный параметр запроса.
- Обеспечить единообразные ошибки авторизации, валидации и конфликтов версий.

**Критерий приёмки:** OpenAPI соответствует фактическому поведению API, а правила авторизации и ошибки проверяются автоматическими тестами.

**Основные области:**
- `frontend/src/App.vue`

**Работы:**

- Реализовать создание и редактирование через CR.

- Показывать пользователю доступные действия в соответствии с полномочиями.
- Обеспечить понятное отображение ошибок валидации и конфликтов версий.

**Критерий приёмки:** основные операции доступны через UI и не обходят серверные правила авторизации.

### Этап 9. Миграция и ввод в эксплуатацию

**Работы:**
- Выполнить миграцию на тестовой копии данных.
- Проверить полноту переноса, ссылки, версии, CR, назначения и аудит.
- Провести функциональные, интеграционные, конкурентные и security-тесты.
- Подготовить процедуру переключения и план отката.
- Провести пробный запуск и документировать результаты.
- После утверждения критериев выполнить переключение на новую модель.

**Критерий приёмки:** подтверждены целостность данных, отсутствие межтенантных утечек, корректность авторизации, сохранность истории и возможность восстановиться по утверждённой процедуре.

## 5. Обязательные регрессионные проверки

1. Tenant isolation для чтения, изменения, поиска, экспорта, счётчиков и справочных данных.
2. Невозможность повторного использования отображаемого номера.
3. Запрет создания связи ОИИ–ИС между tenant.
4. Запрет включения ОИИ в ОИИ.
5. Отсутствие наследования прав через состав ОИИ.
6. Проверка полномочий на управление составом ОИИ.
7. Неизменяемость опубликованных версий.
8. Атомарность применения CR и обновления текущей версии.
9. Обработка двух конкурентных CR на одну базовую версию.
10. Проверка авторизации согласующего и инициатора.
11. Невозможность подменить actor через запрос.
12. Сохранение обсуждений, решений и аудита.
13. Проверка миграции и соответствия количества записей.
14. Проверка FK, CHECK, UNIQUE и NOT NULL на уровне PostgreSQL.
15. Проверка поведения при сбоях транзакций и повторных запросах.

Существующие тесты, в том числе `approval_concurrency_integration_test.go`, `change_request_concurrency_integration_test.go` и `persistence_invariants_integration_test.go`, необходимо сохранить и расширить, а не заменять только тестами нового поведения.

## 7. Необходимые решения до начала миграций

Следующие вопросы требуют явного решения:

1. **Нормативная матрица:** утвердить применимость конкретных положений приказов № 66 и № 130 к категориям ИС/ОИИ и согласовать обязательность каждого атрибута и доказательства.
2. **Формальный статус КВОИ:** определить юридически корректный способ связывать решение о КВОИ с записью AtlasIS или внешним нормативным справочником. Не приравнивать КВОИ к ОИИ и не закреплять это соответствие в DDL без проверки.
3. **Миграция IA:** как однозначно определить тип каждой существующей записи и что делать с неоднозначными случаями.
4. **Организационная модель:** как назначить tenant и организацию для каждой legacy-записи.
5. **Нумерация:** точный формат отображаемых номеров, область уникальности и правила выдачи.
6. **API-совместимость:** сроки и стратегия вывода legacy `/assets`.
7. **OIDC:** стабильность `(iss, sub)`, состав claims и процесс назначения первоначальных полномочий.
8. **Аудит и ретенция:** какие события и данные нельзя удалять, а какие сроки хранения применяются.
9. **Ввод в эксплуатацию:** допустимое окно переключения и требования к откату.

До принятия решений, влияющих на структуру данных и перенос существующих записей, не следует создавать миграцию, которая закрепляет эти решения необратимым образом.

## 8. Правила выполнения работ

- Каждый этап реализуется отдельным обозримым набором изменений.
- Изменения БД выполняются только новыми последовательными миграциями; уже применённые миграции не переписываются.
- Каждая миграция сопровождается проверками целостности и, если применимо, тестом перехода данных.
- Изменения домена, API и схемы должны быть согласованы между собой.
- Тесты должны проверять не только успешные сценарии, но и отказ в доступе, конфликты версий и нарушения ограничений.
- Перед каждым существенным этапом фиксируются критерии приёмки.
- PR не считается завершённым, если документация и roadmap противоречат фактическому поведению.
- Любое расширение объёма работ, меняющее согласованные архитектурные решения, выносится на отдельное согласование.

## 9. Критерий завершения v1

v1 считается готовой, когда:

- ИС и ОИИ реализованы как разные сущности;
- tenant isolation обеспечивается на уровне приложения и подтверждена тестами;
- состав ОИИ управляется через CR и отражается в неизменяемых версиях;
- авторизация основана на проверенной OIDC-идентичности и назначениях с явной областью действия;
- согласования, обсуждения и аудит сохраняются;
- API и UI поддерживают основные процессы реестра;
- существующие данные перенесены либо формально классифицированы как требующие ручного разрешения;
- все критические инварианты покрыты автоматическими тестами;
- документация соответствует реализации;
- процедура ввода в эксплуатацию и отката проверена.
